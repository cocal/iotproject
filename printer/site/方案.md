# 远程打印机项目总体方案

> 状态：设计稿 v0.5（打印专用反向隧道方案）
> 范围：只定义总体架构、领域模型、接口边界和运行流程，不包含实现代码。

## 1. 背景与目标

`iotproject` 是多个物联网项目的总仓库，本文件只描述其中的 `printer` 子项目。

目标是让外部系统提交打印指令，由远程服务端生成打印内容；ESP8266 主动连接远程服务端，通过打印专用隧道接收渲染后的数据并转发给内网打印机，同时提供一个后台 Web 页面查询任务、设备和打印结果。

首版需要解决：

1. 打印指令可以被可靠接收并保存。
2. 打印内容在远程服务端统一渲染，设备端不承担复杂排版。
3. ESP8266 断线重连或重启时不会静默丢单。
4. 后台能够区分“未渲染、待打印、打印中、成功、失败”等状态。
5. 旧 Java 程序中的订单字段和热敏/针式打印布局可以逐步迁移。

## 2. 历史资料结论

历史打印机代码和二进制资料提供了以下约束：

- `Netkk.java` 在本地监听 TCP `7576`，使用 GBK 按行读取文本，收完连接后直接触发打印。
- JAR 中的 `NetworkServer_2` 默认使用 TCP `9600`，同样使用 GBK 按行读取，并以包含“地址”的行作为一份单据的触发标记。现网端口已确认为 **9100**，新服务端兼容入口使用 9100；9600 只作为旧 JAR 的历史默认值记录。
- 旧数据按订单字段和商品明细组织，字段包括序号、时间、客户、清单号、商品名、数量、单位、单价、金额、合计和备注。
- `Tt.java`/`PcpPrinter_2` 将排版写死在 Java AWT 打印代码中，并选择固定打印机名称，例如 `Jolimark FP-570K`。
- 目录中还有芯烨 58/80/76 系列 Linux 驱动，说明历史环境可能包含本地 Linux 打印机驱动和非纯 ESC/POS 打印机。

这些资料说明了业务字段和打印样式来源。新服务端在 9100 上保留独立的旧协议适配器：每个 TCP 连接使用 GBK 按行读取，连接关闭或检测到包含“地址”的行时形成一份原始单据，并将原始报文和解析结果写入 `PrintJob`。内部 API、数据库和设备协议仍使用结构化 JSON、UTF-8 和任务状态记录，避免让历史协议扩散到新模块。

## 3. 总体架构

```text
外部业务系统
      |
      | HTTPS: POST /api/v1/print-commands
      v
远程 VPS
  ├─ 打印请求 API
  ├─ 渲染器
  ├─ 任务队列与状态机
  ├─ 打印隧道网关 :9443
  └─ PostgreSQL
      ^
      | ESP8266 主动建立 TLS TCP 连接
      | VPS 通过已建立的连接下发打印数据
      v
 ESP8266 控制板  --固定 UART/网络接口-->  内网打印机
```

打印主链路只有两个入口：外部系统提交打印参数的 HTTPS API，以及 ESP8266 主动连接的打印专用 TLS TCP 端口。设备不需要公网入站端口，VPS 也不需要建立到设备内网的反向连接。

### 3.1 部署建议

逻辑上分为五个模块，首版部署为两个运行单元：

- `server-api`：打印接入、任务状态、设备连接网关、后台 API，以及 Web 静态文件或 Web 反向代理。
- `render-worker`：从数据库领取待渲染任务，生成可供设备打印的文件或字节流。

数据库使用 PostgreSQL 保存打印任务和投递状态；首版不额外部署 Redis 或消息代理。渲染产物可以存放在服务器文件系统，接口保留对象存储替换点；任务量变大后再评估数据库队列和渲染 Worker 的扩展方式。

### 3.2 ESP8266 任务通信方案比较与决策

打印机在内网，ESP8266 负责主动向 VPS 建立一条打印专用 TLS TCP 长连接。连接建立后是全双工的：ESP8266 发心跳和结果，VPS 直接向该连接写入打印任务数据。ESP8266 不需要判断任意目标地址，也不承担通用内网代理职责；它只把数据转发到本地预配置的打印机接口。

| 方案 | 通信路径与延迟 | 结论 |
| --- | --- | --- |
| HTTPS 轮询 | ESP8266 主动请求服务端；5 秒间隔下，新任务通常在 0--5 秒内被发现 | 实现简单，作为当前代码和断线恢复通道保留 |
| 打印专用反向 TCP 隧道 | ESP8266 主动连接 VPS `9443/TCP`；VPS 通过活动连接推送渲染后的 ESC/POS 数据 | 作为主通道，延迟低，不需要 MQ 或设备入站端口 |

**首版决策：使用打印专用反向 TCP 隧道，不做通用内网代理。** VPS 主链路提供 `POST /api/v1/print-commands` 和设备 TLS TCP `9443` 两个入口。前者接收业务参数并渲染，后者只负责设备鉴权、心跳、打印任务下发和结果回传。现有 HTTPS `poll` 接口在隧道网关完成前继续保留，作为打印任务恢复通道。

TCP 隧道使用带长度的应用层帧，不能把一次 `send` 当成一次完整消息。设备上线后发送设备 ID、固件版本和独立凭据；VPS 登记每台设备的活动连接并通过心跳检测断线。任务帧包含 `task_id`、`lease_id`、数据长度、分块序号和 SHA-256。设备完整接收并校验后回复 `received`，开始向打印机输出前回复 `started`，结束后回复 `completed` 或 `failed`。

连接两端的职责如下：ESP8266 负责 Wi-Fi/TLS、断线重连、帧解析、打印机接口输出和状态上报；VPS 隧道网关负责 TLS 服务端、设备鉴权、活动连接登记和任务下发；Spring Boot 与 PostgreSQL 继续负责任务队列、租约、状态机和重试。连接网关可以和现有 Spring Boot 部署在同一台 VPS 上，不需要单独的消息 Broker。

VPS `443/TCP` 已由 Nginx 提供网站服务，因此设备隧道使用独立的 `9443/TCP`。实现网关时需开放 VPS `nftables` 和云安全组的 `9443/TCP`；设备只需主动出站连接。当前仓库已经实现 HTTPS `poll`，专用 TCP 网关尚未实现。

如果打印机通过 UART/USB 转接连接，ESP8266 将收到的打印字节写入固定串口；如果打印机本身是网络打印机，ESP8266 使用本地配置的固定 IP 和端口连接它。目标路由不从外部请求中动态传入。

## 4. 五个逻辑模块

### 4.1 打印指令接入服务

职责：

- 接受外部系统提交的结构化打印指令。
- 校验打印模板、打印机目标、业务单号和幂等键。
- 创建 `PrintJob`，初始状态为 `accepted`。
- 提供查询单个任务和提交结果的接口。

不负责排版，也不直接连接 ESP8266。接入成功只代表任务已持久化，不代表已经打印。

推荐入口：`POST /api/v1/print-commands`。

兼容入口：TCP `0.0.0.0:9100`，编码 GBK，消息为换行分隔的文本。兼容入口不依赖 HTTP 返回值；接收完成后先持久化任务，再由队列异步渲染和打印。

### 4.2 打印文件渲染服务

职责：

- 根据模板、订单数据和打印机能力生成打印产物。
- 处理纸张宽度（例如 58/76/80 mm）、字体、中文编码、换行、分页和二维码/条码。
- 记录渲染版本、模板版本和产物校验值。
- 渲染失败时保存可读错误原因，并允许后台重试。

首版建议生成打印机可以直接执行的 `ESC/POS` 字节流；ESP8266 只需流式转发，不需要理解 PDF 或图片。若某型号打印机需要 Linux 驱动或 Java AWT/CUPS，则把它作为服务端的另一个渲染/打印适配器，不强行让 ESP8266 解析桌面打印协议。

同一任务可以同时生成两种产物：

- `device_artifact`：给 ESP8266 打印的设备格式，首选 ESC/POS。
- `preview_artifact`：给后台预览的 PDF/PNG，可选，不参与设备投递。

### 4.3 ESP8266 打印隧道网关

职责：

- 接受 ESP8266 主动建立的 TLS TCP 连接，完成设备鉴权和心跳维护。
- 设备上线时登记活动连接；断开或心跳超时时清除连接状态。
- 收到新任务后为目标设备原子领取任务，并通过活动连接发送任务元数据和打印数据。
- 为任务发放短期租约，避免设备掉线后任务永久卡住。
- 接收设备的 `received`、`started`、`completed`、`failed` 事件。
- 根据设备状态和租约结果安排重试。
- 保留 HTTPS 轮询 API，作为隧道不可用时的打印任务恢复通道。

现有 HTTPS 恢复接口：

```text
POST /api/v1/devices/{device_id}/poll
POST /api/v1/devices/{device_id}/tasks/{task_id}/events
GET  /api/v1/devices/{device_id}/tasks/{task_id}/artifact
```

现有 HTTPS 恢复接口使用 `X-Device-Key` 独立鉴权，租约默认 120 秒。未来 TCP 隧道使用每设备独立凭据鉴权；应用层帧至少包含设备 ID、消息类型、长度、任务 ID 和租约 ID。TCP ACK 只代表网络栈收到数据，不能代替打印结果确认。

### 4.4 ESP8266 本地打印代理

职责：

- 以设备凭据主动建立 TLS TCP 长连接；网络失败时指数退避并持续重连。
- 保持连接心跳，解析有长度边界的任务帧；隧道断开期间使用 HTTPS 轮询恢复打印任务。
- 收到任务后校验任务 ID、字节数和 SHA-256 校验值。
- 将打印字节流通过固定 UART、USB 转接或固定的打印机网络接口发送给打印机。
- 在本地记录最近完成的任务 ID，防止重启后重复打印。
- 上报打印机缺纸、离线、串口错误、超时等可观测状态。

ESP8266 不负责模板解析、PDF 解析或中文排版，也不接受外部传入的任意目标地址和端口。若实际打印机只有 USB/CUPS 接口而没有 ESP8266 可用的串口/网络接口，需要增加本地 Linux 打印网关。

### 4.5 后台 Web 查询页面

首版以查询和运维为主，页面至少包括：

- 任务列表：按时间、业务单号、设备、状态筛选。
- 任务详情：原始指令、渲染信息、投递尝试、错误信息和时间线。
- 设备列表：在线状态、最后连接/心跳时间、固件版本、打印机状态。
- 任务详情中的预览图或 PDF（如果生成了 `preview_artifact`）。
- 重试渲染、重试投递、取消未执行任务。

后台操作必须经过权限控制，并记录操作人和操作时间。页面不直接访问设备，也不绕过任务状态机写数据库。

## 5. 核心领域模型

### 5.1 实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `PrintJob` 打印任务 | 一次业务打印请求 | `id`、`idempotency_key`、`source`、`template_id`、`payload`、`target_device_id`、`status`、时间戳 |
| `PrintTemplate` 打印模板 | 定义数据到打印内容的映射 | `id`、`version`、`format`、`paper_width`、启用状态 |
| `RenderedArtifact` 渲染产物 | 某任务的设备文件或预览文件 | `job_id`、`kind`、`media_type`、`size`、`sha256`、存储位置 |
| `Device` 设备 | 一个 ESP8266 控制板 | `id`、设备凭据、固件版本、能力、最后在线时间 |
| `Printer` 打印机 | 连接在设备上的打印机 | 型号、连接类型、纸宽、协议、状态 |
| `DeliveryAttempt` 投递尝试 | 一次设备领取和执行记录 | `job_id`、`device_id`、租约、开始/结束时间、结果、错误 |
| `AuditEvent` 审计事件 | 重要状态和后台操作记录 | 操作者、动作、对象、时间、结果 |

### 5.2 任务状态

```text
accepted -> rendering -> queued -> leased -> printing -> succeeded
               |           |          |          |
               v           v          v          v
          render_failed  cancelled  expired  failed
```

建议将渲染状态和投递状态分别存储，业务展示再汇总为任务状态。这样渲染成功但设备暂时离线时，任务仍然明确处于 `queued`，不会被误判为失败。

状态约束：

- `accepted`：指令已保存，尚未开始渲染。
- `rendering`：有一个渲染 Worker 持有渲染租约。
- `queued`：已生成设备产物，等待目标设备可用连接领取。
- `leased`：设备已领取，服务端等待设备确认开始或完成。
- `printing`：设备已开始向打印机输出。
- `succeeded`：设备确认打印机完成。
- `render_failed`：渲染失败，可修复后重试。
- `failed`：设备或打印机执行失败，按策略重试或人工处理。
- `expired`：设备租约超时，任务回到 `queued` 或进入失败重试。
- `cancelled`：尚未实际打印的任务被取消。

## 6. 打印专用隧道与可靠投递

### 6.1 隧道连接流程

1. ESP8266 主动连接 VPS `9443/TCP`，完成 TLS 服务端证书校验和设备鉴权。
2. VPS 登记 `device_id -> active connection`，双方开始发送心跳。
3. 连接断开或心跳超时后，VPS 清除活动连接；设备按指数退避重连。
4. 隧道只承载打印任务帧、设备心跳和打印结果，不承载任意目标地址/端口代理流。

### 6.2 一次打印任务流程

1. 外部系统调用 `POST /api/v1/print-commands`，服务端保存参数并生成 ESC/POS 产物。
2. 任务进入 `queued`；隧道网关找到目标设备的活动连接并原子领取任务，创建 `lease_id`。
3. VPS 发送 `TASK_BEGIN` 和分块 `TASK_DATA`；ESP8266 接收完整产物、校验长度和 SHA-256 后回复 `received`。
4. ESP8266 向固定打印机接口输出前上报 `started`，输出完成后上报 `completed` 或 `failed`。
5. 服务端记录投递尝试，任务进入终态或按租约/重试策略重新排队。

### 6.3 断网、重启和重复任务

- 隧道断开时不能仅根据 TCP 断开判断打印成功；没有 `completed` 的任务由租约回收和重试处理。
- 设备在本地保存最近若干个已完成任务 ID。服务端重复发送同一个任务时，设备只确认已完成，不再次打印。
- 任务传输采用至少一次投递语义；打印机已经出纸但完成 ACK 丢失时，后台需要人工确认，不能盲目重打。
- 若打印耗时可能超过 120 秒，应增加租约续期帧或调整租约时长。

### 6.4 设备响应大小

ESP8266 内存有限，不能假设一次消息可以装下完整 PDF 或大图片。打印产物应分块发送（建议每块 1--4 KB）；设备可以使用 LittleFS 暂存，完整校验后再输出，避免连接中断时打印半份内容。

## 7. 接口约定草案

### 7.1 提交打印指令

```json
POST /api/v1/print-commands
{
  "idempotency_key": "order-20261024-0001",
  "template_id": "receipt-v1",
  "target_device_id": "printer-room-1",
  "data": {
    "order_no": "A0001",
    "customer_name": "客户",
    "items": [
      {"name": "商品", "quantity": 2, "unit": "件", "unit_price": "10.00"}
    ],
    "total": "20.00",
    "note": "备注"
  }
}
```

响应只确认任务已经持久化：

```json
{"job_id": "job_01...", "status": "accepted"}
```

### 7.2 HTTPS 轮询恢复响应

下面的轮询接口是当前代码已经实现的临时恢复通道；专用 TLS TCP 隧道网关尚未实现。正常情况下，设备保持长连接接收服务端推送的打印任务。

```json
{
  "server_time": "2026-10-24T12:00:00Z",
  "poll_after_ms": 5000,
  "task": {
    "task_id": "job_01...",
    "lease_id": "lease_01...",
    "expires_at": "2026-10-24T12:02:00Z",
    "artifact_url": "/api/v1/devices/printer-room-1/tasks/job_01.../artifact",
    "size": 1832,
    "sha256": "...",
    "format": "escpos"
  }
}
```

无任务时 `task` 为 `null`。仅在长连接无法建立或断开时使用恢复轮询；服务端可以通过 `poll_after_ms` 调整间隔。

## 8. 安全与运维

- 外部 API 和设备 API 全部使用 HTTPS。
- 每台 ESP8266 使用独立设备 ID 和密钥；服务端不能用一个共享密钥代表所有设备。
- 设备接口只允许访问自己的任务和产物，后台接口使用独立账号/角色；打印隧道只接受设备连接，不提供通用目标代理。
- 打印数据按 JSON Schema 校验，限制字段长度、明细行数和产物大小，避免异常请求拖垮渲染 Worker。
- 记录结构化日志：任务 ID、设备 ID、租约 ID、状态变化和错误码，不把完整敏感打印内容写入普通日志。
- 监控待渲染数量、队列等待时间、渲染失败率、设备在线率、任务重试次数和打印成功率。
- 数据库定期备份；打印产物设置保留周期，避免磁盘无限增长。

## 9. 分阶段实施建议

### 阶段一：最小闭环

- 一个模板、一个设备、一个打印机型号。
- 接入 API、PostgreSQL 任务表、ESC/POS 渲染、专用 TLS TCP 打印隧道和完成/失败上报。
- 后台只提供任务和设备查询。
- 使用设备独立凭据；设备到服务端采用 TLS，HTTPS 轮询作为断线恢复通道。

### 阶段二：可运维化

- 模板版本和预览产物。
- 任务重试、取消、手动重打和审计记录。
- 设备能力上报、打印机状态和更完整的后台筛选。
- 旧 TCP/GBK 协议适配器，作为迁移期兼容层。

### 阶段三：多设备与多型号

- 多打印机配置和渲染适配器。
- 分组、优先级、按设备路由和并发控制。
- 对大文件增加断点续传和对象存储。
- 必要时拆分渲染 Worker 与任务存储层。

## 10. 需要在实现前确认的问题

1. ESP8266 与打印机的实际连接方式是 UART、USB 转接、网络，还是通过本地 Linux 主机？这决定设备代理能否直接发送 ESC/POS。
2. 首台打印机的准确型号、纸宽和控制协议是什么？芯烨 58/80/76 系列与 `Jolimark FP-570K` 不能默认使用同一渲染器。
3. 打印内容是否只包含订单小票，还是还需要图片、二维码、条码、PDF 等格式？
4. 外部提交方是否已有固定的 TCP/GBK 协议，是否需要首版兼容端口 `7576` 或 `9600`？
5. 一个任务是否允许指定设备，还是由服务端按设备组/打印机类型自动路由？
6. “打印完成”的定义是 ESP8266 发完字节，还是需要打印机提供真实的出纸/故障反馈？
7. 是否需要用户登录、多个角色和远程重打权限？

在这些问题确认前，本文中的接口路径和字段名属于方案草案，不作为最终兼容承诺。

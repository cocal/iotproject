# 远程打印机项目总体方案

> 状态：设计稿 v0.6（ESP8266 通用反向 TCP 代理方案）
> 范围：只定义总体架构、领域模型、接口边界和运行流程，不包含实现代码。

## 1. 背景与目标

`iotproject` 是多个物联网项目的总仓库，本文件只描述其中的 `printer` 子项目。

目标是让外部系统提交打印指令，由远程服务端生成打印内容；ESP8266 主动连接远程服务端，通过反向 TCP 隧道接收打印任务，并按授权连接设备所在内网的 TCP 服务，同时提供一个后台 Web 页面查询任务、设备和打印结果。

首版需要解决：

1. 打印指令可以被可靠接收并保存。
2. 打印内容在远程服务端统一渲染，设备端不承担复杂排版。
3. ESP8266 断线重连或重启时不会静默丢单。
4. 后台能够区分“未渲染、待打印、打印中、成功、失败”等状态。
5. 旧 Java 程序中的订单字段和热敏/针式打印布局可以逐步迁移。
6. ESP8266 能在授权范围内代理访问内网 TCP 服务。

## 2. 历史资料结论

历史打印机代码和二进制资料提供了以下约束：

- `Netkk.java` 在本地监听 TCP `7576`，使用 GBK 按行读取文本，收完连接后直接触发打印。
- JAR 中的 `NetworkServer_2` 默认使用 TCP `9600`，同样使用 GBK 按行读取，并以包含“地址”的行作为一份单据的触发标记。现网端口已确认为 **9100**，新服务端兼容入口使用 9100；9600 只作为旧 JAR 的历史默认值记录。
- 旧数据按订单字段和商品明细组织，字段包括序号、时间、客户、清单号、商品名、数量、单位、单价、金额、合计和备注。
- `Tt.java`/`PcpPrinter_2` 将排版写死在 Java AWT 打印代码中，并选择固定打印机名称，例如 `Jolimark FP-570K`。
- 目录中还有芯烨 58/80/76 系列 Linux 驱动，说明历史环境可能包含本地 Linux 打印机驱动和非纯 ESC/POS 打印机。

这些资料说明了业务字段和打印样式来源。新服务端在 9100 上保留独立的旧协议适配器：每个 TCP 连接使用 GBK 按行读取，连接关闭或检测到包含“地址”的行时形成一份原始单据，并将原始报文和解析结果写入 `PrintJob`。内部 API、数据库和设备协议仍使用结构化 JSON、UTF-8 和任务状态记录，避免让历史协议扩散到新模块。

## 3. 总体架构

```text
外部业务系统
      |
      | HTTPS: POST /api/v1/print-commands
      v
远程 VPS
  ├─ 打印请求 API
  ├─ 渲染器
  ├─ 任务队列与状态机
  ├─ 反向 TCP 隧道网关 :9443
  └─ PostgreSQL
      ^
      | ESP8266 主动建立 TLS TCP 连接
      | 打印任务 + OPEN/DATA/CLOSE 代理帧
      v
 ESP8266 控制板
      ├─ 固定打印机接口
      └─ 授权的内网 TCP 服务
```

打印主链路的两个入口是外部系统提交打印参数的 HTTPS API，以及 ESP8266 主动连接的 TLS TCP 隧道端口。通用代理的运维入口只绑定 VPS 本机地址或受保护的 SSH/VPN 网络，不直接作为公网开放代理。

### 3.1 部署建议

逻辑上分为五个模块，首版部署为两个运行单元：

- `server-api`：打印接入、任务状态、设备连接网关、后台 API，以及 Web 静态文件或 Web 反向代理。
- `render-worker`：从数据库领取待渲染任务，生成可供设备打印的文件或字节流。

数据库使用 PostgreSQL 保存打印任务和投递状态；首版不额外部署 Redis 或消息代理。渲染产物可以存放在服务器文件系统，接口保留对象存储替换点；任务量变大后再评估数据库队列和渲染 Worker 的扩展方式。

### 3.2 ESP8266 任务通信与反向 TCP 代理方案

ESP8266 主动向 VPS 建立 TLS TCP 长连接。连接建立后是全双工的：VPS 可以通过该连接发送打印任务，也可以发送一个目标地址和端口，让 ESP8266 主动连接内网目标并双向转发 TCP 数据。

| 方案 | 通信路径与延迟 | 适用范围 | 主要限制 |
| --- | --- | --- | --- |
| HTTPS 轮询 | ESP8266 主动请求服务端；5 秒间隔下，新任务通常在 0--5 秒内被发现 | 打印任务恢复、设备规模小、允许秒级延迟 | 空闲请求多，不能承载持续 TCP 流 |
| 打印专用隧道 | VPS 通过 TLS 长连接推送 ESC/POS；ESP8266 转发到固定打印机接口 | 打印主链路 | 只能访问固定打印机接口 |
| 通用反向 TCP 代理 | VPS 发送 `OPEN(target_ip, target_port)`；ESP8266 主动连接内网目标，再转发 `DATA` | 远程访问授权的 HTTP、SSH、打印机或其他 TCP 服务 | ESP8266 内存、TLS 缓冲和 Wi-Fi 吞吐有限，首版不做多路高并发 |

**方案决策：实现通用反向 TCP 代理，但首版限制为每台 ESP8266 一个活动代理流。** 一条设备到 VPS 的 TLS 连接同时承载控制帧、打印任务帧和一个代理数据流；代理流关闭后才能开始下一条代理流。这样不需要 MQ，也不需要设备入站端口，协议和内存占用都可控。后续实测稳定后，再考虑多路复用。

“一个活动代理流”不等于只能处理一个打印指令。VPS 可以持续接收多个打印请求，`PrintJob` 在 PostgreSQL 中排队；ESP8266 一次领取一个打印任务，收到 `completed`/`failed` 后再领取下一个。首版如果代理流正在占用数据通道，新的打印任务等待代理流关闭；如果需要代理和打印并发，再增加第二条 TLS 连接或实现应用层多路复用。

VPS 的业务入口仍是 `POST /api/v1/print-commands`，设备隧道使用独立 `9443/TCP`。VPS 上的代理入口只监听 `127.0.0.1`，或放在 SSH/VPN 后面；它不直接暴露为无认证公网 SOCKS5。现有 HTTPS `poll` 接口在隧道网关完成前继续保留，作为打印任务恢复通道。

首版代理只转发字节，不解析目标协议。帧使用长度边界和 `stream_id`；控制消息包括 `AUTH`、`OPEN`、`OPEN_OK`、`OPEN_ERROR`、`DATA`、`CLOSE`、`RESET`、`PING` 和 `PONG`。第一版每台设备只允许一个 `stream_id`，避免 ESP8266 同时保存多个 TCP socket 和多组缓冲区。

性能上，ESP8266 适合低到中等吞吐的单连接场景，例如打印机、简单 HTTP 管理页、SSH 小流量维护。不能先假定它适合大文件持续传输、多个并发连接、RDP 或高带宽代理；需要用真实硬件测试 TLS 长连接、内网目标连接、双向吞吐、断线重连和长期运行时的剩余堆内存。若需要多连接或高吞吐，优先换 ESP32 或本地 Linux 网关。

实现网关时需开放 VPS `nftables` 和云安全组的 `9443/TCP`；设备只需主动出站连接。VPS `443/TCP` 继续由 Nginx 提供网站服务。

## 4. 五个逻辑模块

### 4.1 打印指令接入服务

职责：

- 接受外部系统提交的结构化打印指令。
- 校验打印模板、打印机目标、业务单号和幂等键。
- 创建 `PrintJob`，初始状态为 `accepted`。
- 提供查询单个任务和提交结果的接口。

不负责排版，也不直接连接 ESP8266。接入成功只代表任务已持久化，不代表已经打印。

推荐入口：`POST /api/v1/print-commands`。

兼容入口：TCP `0.0.0.0:9100`，编码 GBK，消息为换行分隔的文本。兼容入口不依赖 HTTP 返回值；接收完成后先持久化任务，再由队列异步渲染和打印。

### 4.2 打印文件渲染服务

职责：

- 根据模板、订单数据和打印机能力生成打印产物。
- 处理纸张宽度（例如 58/76/80 mm）、字体、中文编码、换行、分页和二维码/条码。
- 记录渲染版本、模板版本和产物校验值。
- 渲染失败时保存可读错误原因，并允许后台重试。

首版建议生成打印机可以直接执行的 `ESC/POS` 字节流；ESP8266 只需流式转发，不需要理解 PDF 或图片。若某型号打印机需要 Linux 驱动或 Java AWT/CUPS，则把它作为服务端的另一个渲染/打印适配器，不强行让 ESP8266 解析桌面打印协议。

同一任务可以同时生成两种产物：

- `device_artifact`：给 ESP8266 打印的设备格式，首选 ESC/POS。
- `preview_artifact`：给后台预览的 PDF/PNG，可选，不参与设备投递。

### 4.3 ESP8266 反向 TCP 隧道网关

职责：

- 接受 ESP8266 主动建立的 TLS TCP 连接，完成设备鉴权和心跳维护。
- 设备上线时登记活动连接；断开或心跳超时时清除连接状态。
- 接收已认证的代理请求，检查目标地址/端口策略，并通过设备连接发送 `OPEN`。
- 接收设备返回的 `OPEN_OK`/`OPEN_ERROR`，在 VPS 本地代理入口与设备流之间双向转发 `DATA`。
- 首版每台设备限制一个活动代理流，设置帧大小、空闲超时、连接数和速率上限。
- 收到打印任务后为目标设备原子领取任务，并通过活动连接发送任务帧。
- 为打印任务发放短期租约，接收 `received`、`started`、`completed`、`failed` 事件并安排重试。
- 保留 HTTPS 轮询 API，作为隧道不可用时的打印任务恢复通道。

现有 HTTPS 恢复接口：

```text
POST /api/v1/devices/{device_id}/poll
POST /api/v1/devices/{device_id}/tasks/{task_id}/events
GET  /api/v1/devices/{device_id}/tasks/{task_id}/artifact
```

现有 HTTPS 接口使用 `X-Device-Key`，租约默认 120 秒。未来 TCP 隧道使用每设备独立凭据；应用层帧包含消息类型、长度、`stream_id`，打印任务帧额外包含任务 ID和租约 ID。TCP ACK 只代表网络栈收到数据，不能代替打印结果确认。

### 4.4 ESP8266 本地代理与打印代理

职责：

- 以设备凭据主动建立 TLS TCP 长连接；网络失败时指数退避并持续重连。
- 保持心跳，解析有长度边界的帧；首版同时只维护一个内网代理 socket。
- 收到 `OPEN` 后校验目标地址/端口，再主动连接局域网目标；双方数据通过 `DATA` 帧转发。
- 收到打印任务后校验任务 ID、字节数和 SHA-256，并将数据转发到固定 UART、USB 转接或固定的打印机网络接口。
- 在本地记录最近完成的打印任务 ID，防止重启后重复打印。
- 上报内网目标连接错误、打印机缺纸、离线、串口错误和超时等状态。

第一版不做 DNS 目标解析，不允许外部请求覆盖设备端的本地目标策略。ESP8266 不负责模板解析、PDF 解析或中文排版。

### 4.5 后台 Web 查询页面

首版以查询和运维为主，页面至少包括：

- 任务列表：按时间、业务单号、设备、状态筛选。
- 任务详情：原始指令、渲染信息、投递尝试、错误信息和时间线。
- 设备列表：在线状态、最后连接/心跳时间、固件版本、打印机状态。
- 任务详情中的预览图或 PDF（如果生成了 `preview_artifact`）。
- 重试渲染、重试投递、取消未执行任务。

后台操作必须经过权限控制，并记录操作人和操作时间。页面不直接访问设备，也不绕过任务状态机写数据库。

## 5. 核心领域模型

### 5.1 实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `PrintJob` 打印任务 | 一次业务打印请求 | `id`、`idempotency_key`、`source`、`template_id`、`payload`、`target_device_id`、`status`、时间戳 |
| `PrintTemplate` 打印模板 | 定义数据到打印内容的映射 | `id`、`version`、`format`、`paper_width`、启用状态 |
| `RenderedArtifact` 渲染产物 | 某任务的设备文件或预览文件 | `job_id`、`kind`、`media_type`、`size`、`sha256`、存储位置 |
| `Device` 设备 | 一个 ESP8266 控制板 | `id`、设备凭据、固件版本、能力、最后在线时间 |
| `Printer` 打印机 | 连接在设备上的打印机 | 型号、连接类型、纸宽、协议、状态 |
| `DeliveryAttempt` 投递尝试 | 一次设备领取和执行记录 | `job_id`、`device_id`、租约、开始/结束时间、结果、错误 |
| `AuditEvent` 审计事件 | 重要状态和后台操作记录 | 操作者、动作、对象、时间、结果 |

### 5.2 任务状态

```text
accepted -> rendering -> queued -> leased -> printing -> succeeded
               |           |          |          |
               v           v          v          v
          render_failed  cancelled  expired  failed
```

建议将渲染状态和投递状态分别存储，业务展示再汇总为任务状态。这样渲染成功但设备暂时离线时，任务仍然明确处于 `queued`，不会被误判为失败。

状态约束：

- `accepted`：指令已保存，尚未开始渲染。
- `rendering`：有一个渲染 Worker 持有渲染租约。
- `queued`：已生成设备产物，等待目标设备可用连接领取。
- `leased`：设备已领取，服务端等待设备确认开始或完成。
- `printing`：设备已开始向打印机输出。
- `succeeded`：设备确认打印机完成。
- `render_failed`：渲染失败，可修复后重试。
- `failed`：设备或打印机执行失败，按策略重试或人工处理。
- `expired`：设备租约超时，任务回到 `queued` 或进入失败重试。
- `cancelled`：尚未实际打印的任务被取消。

## 6. 反向 TCP 代理与打印任务流程

### 6.1 内网 TCP 代理流程

1. ESP8266 主动连接 VPS `9443/TCP`，完成 TLS 服务端证书校验和设备鉴权，随后发送心跳。
2. 运维用户通过 SSH/VPN 访问 VPS 上仅监听本机的代理入口，并指定已授权的设备、目标 IPv4 地址和端口。
3. VPS 为该请求分配 `stream_id`，向对应设备发送 `OPEN(stream_id, target_ip, target_port)`。
4. ESP8266 校验目标策略，并在局域网内主动建立一个 TCP socket；成功返回 `OPEN_OK`，失败返回 `OPEN_ERROR`。
5. VPS 与 ESP8266 将两端数据包装为 `DATA(stream_id, bytes)`；首版只允许一个活动流，并用背压限制缓冲区。
6. 任一端关闭时发送 `CLOSE`；异常或超时发送 `RESET`，释放本地 socket 和流状态。

代理流是临时会话，不创建 `PrintJob`，也不由打印任务租约重试。隧道断开后代理流结束，客户端需要自行重连。

### 6.2 一次打印任务流程

1. 外部系统调用 `POST /api/v1/print-commands`，服务端保存参数并生成 ESC/POS 产物；多个请求可以同时进入 `PrintJob` 队列。
2. 任务进入 `queued`；隧道网关在没有代理流占用设备通道时，原子领取一个任务并创建 `lease_id`。
3. VPS 发送 `TASK_BEGIN` 和分块 `TASK_DATA`；ESP8266 接收完整产物、校验长度和 SHA-256 后回复 `received`。
4. ESP8266 向固定打印机接口输出前上报 `started`，输出结束后上报 `completed` 或 `failed`。
5. 服务端记录投递尝试；当前任务完成后，调度器再领取下一个 `queued` 任务。

### 6.3 断网、重启和重复任务

- 隧道断开时不能仅根据 TCP 断开判断打印成功；没有 `completed` 的打印任务由租约回收和重试处理。
- 代理流断开只关闭该流，不影响任务状态；设备重连后可重新建立代理流。
- 设备保存最近完成的打印任务 ID。重复收到同一任务时只确认已完成，不再次打印。
- 任务传输采用至少一次投递语义；打印机已经出纸但完成 ACK 丢失时，后台需要人工确认。
- 若打印耗时可能超过 120 秒，应增加租约续期帧或调整租约时长。

### 6.4 ESP8266 性能边界

首版按一个设备一个 TLS 上游连接、一个内网 TCP socket、一个打印机输出通道设计。代理数据帧从 512--1460 字节范围测试，使用固定大小环形缓冲和背压；不能让慢速目标持续堆积数据。验收需要记录 TLS 建连时间、双向吞吐、断线重连、长时间运行和剩余堆内存。若实际需要多连接、高吞吐或大文件传输，应换 ESP32 或 Linux 网关。

若打印机走 UART，基础组合是一个 VPS TLS socket 加一个代理目标 socket，ESP8266 的资源压力相对可控；若打印机本身也走网络 TCP，则还要同时维护打印机 socket，首版应将代理流和网络打印串行化，除非实机测试证明三条连接和对应缓冲仍稳定。

## 7. 接口约定草案

### 7.1 提交打印指令

```json
POST /api/v1/print-commands
{
  "idempotency_key": "order-20261024-0001",
  "template_id": "receipt-v1",
  "target_device_id": "printer-room-1",
  "data": {
    "order_no": "A0001",
    "customer_name": "客户",
    "items": [
      {"name": "商品", "quantity": 2, "unit": "件", "unit_price": "10.00"}
    ],
    "total": "20.00",
    "note": "备注"
  }
}
```

响应只确认任务已经持久化：

```json
{"job_id": "job_01...", "status": "accepted"}
```

### 7.2 HTTPS 轮询恢复响应

下面的轮询接口是当前代码已经实现的临时恢复通道；反向 TCP 隧道网关尚未实现。正常情况下，设备保持长连接接收打印任务和代理控制帧。

```json
{
  "server_time": "2026-10-24T12:00:00Z",
  "poll_after_ms": 5000,
  "task": {
    "task_id": "job_01...",
    "lease_id": "lease_01...",
    "expires_at": "2026-10-24T12:02:00Z",
    "artifact_url": "/api/v1/devices/printer-room-1/tasks/job_01.../artifact",
    "size": 1832,
    "sha256": "...",
    "format": "escpos"
  }
}
```

无任务时 `task` 为 `null`。仅在长连接无法建立或断开时使用恢复轮询；服务端可以通过 `poll_after_ms` 调整间隔。

## 8. 安全与运维

- 外部 API 和设备 API 全部使用 HTTPS。
- 每台 ESP8266 使用独立设备 ID 和密钥；服务端不能用一个共享密钥代表所有设备。
- 设备接口只允许访问自己的任务和产物，后台接口使用独立账号/角色；反向代理入口必须经过 SSH/VPN 和目标策略控制。
- 打印数据按 JSON Schema 校验，限制字段长度、明细行数和产物大小，避免异常请求拖垮渲染 Worker。
- 记录结构化日志：任务 ID、设备 ID、租约 ID、状态变化和错误码，不把完整敏感打印内容写入普通日志。
- 监控待渲染数量、队列等待时间、渲染失败率、设备在线率、任务重试次数和打印成功率。
- 数据库定期备份；打印产物设置保留周期，避免磁盘无限增长。

## 9. 分阶段实施建议

### 阶段一：最小闭环

- 一个模板、一个设备、一个打印机型号。
- 接入 API、PostgreSQL 任务表、ESC/POS 渲染、反向 TCP 代理隧道和完成/失败上报。
- 后台只提供任务和设备查询。
- 使用设备独立凭据；设备到服务端采用 TLS，HTTPS 轮询作为断线恢复通道。

### 阶段二：可运维化

- 模板版本和预览产物。
- 任务重试、取消、手动重打和审计记录。
- 设备能力上报、打印机状态和更完整的后台筛选。
- 旧 TCP/GBK 协议适配器，作为迁移期兼容层。

### 阶段三：多设备与多型号

- 多打印机配置和渲染适配器。
- 分组、优先级、按设备路由和并发控制。
- 对大文件增加断点续传和对象存储。
- 必要时拆分渲染 Worker 与任务存储层。

## 10. 需要在实现前确认的问题

1. ESP8266 与打印机的实际连接方式是 UART、USB 转接、网络，还是通过本地 Linux 主机？这决定设备代理能否直接发送 ESC/POS。
2. 首台打印机的准确型号、纸宽和控制协议是什么？芯烨 58/80/76 系列与 `Jolimark FP-570K` 不能默认使用同一渲染器。
3. 打印内容是否只包含订单小票，还是还需要图片、二维码、条码、PDF 等格式？
4. 外部提交方是否已有固定的 TCP/GBK 协议，是否需要首版兼容端口 `7576` 或 `9600`？
5. 一个任务是否允许指定设备，还是由服务端按设备组/打印机类型自动路由？
6. “打印完成”的定义是 ESP8266 发完字节，还是需要打印机提供真实的出纸/故障反馈？
7. 是否需要用户登录、多个角色和远程重打权限？

在这些问题确认前，本文中的接口路径和字段名属于方案草案，不作为最终兼容承诺。

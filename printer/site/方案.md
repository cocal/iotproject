# 远程打印机项目总体方案

> 状态：设计稿 v0.9（通用 TCP 网关与最小隧道协议）
> 范围：只定义总体架构、领域模型、接口边界和运行流程，不包含实现代码。

## 1. 背景与目标

`iotproject` 是多个物联网项目的总仓库，本文件只描述其中的 `printer` 子项目。

目标是让外部系统提交打印指令，由远程服务端生成打印内容；ESP8266 主动连接远程服务端，通过反向 TCP 隧道按目标 IP/端口连接内网 TCP 服务并原样转发字节；打印业务留在 VPS，同时提供一个后台 Web 页面查询任务、设备和打印结果。

首版需要解决：

1. 打印指令可以被可靠接收并保存。
2. 打印内容在远程服务端统一渲染，设备端不承担复杂排版。
3. ESP8266 断线重连或重启时不会静默丢单。
4. 后台能够区分“未渲染、待打印、打印中、成功、失败”等状态。
5. 旧 Java 程序中的订单字段和热敏/针式打印布局可以逐步迁移。
6. ESP8266 能在授权范围内代理访问内网 TCP 服务。

## 2. 历史资料结论

历史打印机代码和二进制资料提供了以下约束：

- `Netkk.java` 在本地监听 TCP `7576`，使用 GBK 按行读取文本，收完连接后直接触发打印。
- JAR 中的 `NetworkServer_2` 默认使用 TCP `9600`，同样使用 GBK 按行读取，并以包含“地址”的行作为一份单据的触发标记。现网端口已确认为 **9100**，新服务端兼容入口使用 9100；9600 只作为旧 JAR 的历史默认值记录。
- 旧数据按订单字段和商品明细组织，字段包括序号、时间、客户、清单号、商品名、数量、单位、单价、金额、合计和备注。
- `Tt.java`/`PcpPrinter_2` 将排版写死在 Java AWT 打印代码中，并选择固定打印机名称，例如 `Jolimark FP-570K`。
- 目录中还有芯烨 58/80/76 系列 Linux 驱动，说明历史环境可能包含本地 Linux 打印机驱动和非纯 ESC/POS 打印机。

这些资料说明了业务字段和打印样式来源。新服务端在 9100 上保留独立的旧协议适配器：每个 TCP 连接使用 GBK 按行读取，连接关闭或检测到包含“地址”的行时形成一份原始单据，并将原始报文和解析结果写入 `PrintJob`。内部 API、数据库和设备协议仍使用结构化 JSON、UTF-8 和任务状态记录，避免让历史协议扩散到新模块。

## 3. 总体架构

```text
外部业务系统
      |
      | HTTPS: POST /api/v1/print-commands
      v
远程 VPS
  ├─ 打印请求 API
  ├─ 渲染器
  ├─ 任务队列与状态机
  ├─ 反向 TCP 隧道网关 :9443
  └─ PostgreSQL
      ^
      | ESP8266 主动建立 TLS TCP 连接
      | OPEN / DATA / FIN + 心跳（不携带打印业务指令）
      v
 ESP8266 通用 TCP 网关
      └─ 授权的内网 TCP 服务（含网络打印机）
```

打印主链路的两个入口是外部系统提交打印参数的 HTTPS API，以及 ESP8266 主动连接的 TLS TCP 隧道端口。通用代理的运维入口只绑定 VPS 本机地址或受保护的 SSH/VPN 网络，不直接作为公网开放代理。

### 3.1 部署建议

逻辑上分为五个模块，首版部署为两个运行单元：

- `server-api`：打印接入、任务状态、设备连接网关、后台 API，以及 Web 静态文件或 Web 反向代理。
- `render-worker`：从数据库领取待渲染任务，生成可供设备打印的文件或字节流。

数据库使用 PostgreSQL 保存打印任务和投递状态；首版不额外部署 Redis 或消息代理。渲染产物可以存放在服务器文件系统，接口保留对象存储替换点；任务量变大后再评估数据库队列和渲染 Worker 的扩展方式。

### 3.2 通用反向 TCP 代理决策

ESP8266 主动建立 VPS `9443/TCP` 的 TLS 长连接；VPS 在 OPEN 帧中指定内网 IPv4/端口，8266 连接后原样转发 DATA。TLS 使用成熟库，不自行实现加密；板端建议 ESP8266 Arduino Core 的 BearSSL WiFiClientSecure，VPS 使用服务端 TLS。TLS 加密覆盖 VPS↔8266；8266↔目标为目标协议自身的 TCP（RAW 通常明文，HTTPS/SSH 可另行加密）。

**首版一台设备最多一个活动目标 TCP 流；心跳和流控在数据帧之间交错处理。** 设备不接收打印任务，不存储文件，不理解 ESC/POS、IPP、任务 ID、租约、完成确认或扫描协议。VPS 统一管理任务、产物、扫描、识别和授权。无需 MQ，无设备入站端口；实现时再配置 VPS 防火墙和云安全组 9443。

首版消息为 AUTH/AUTH_OK/AUTH_ERROR、OPEN/OPEN_OK/OPEN_ERROR、DATA、WINDOW_UPDATE、FIN/CLOSED/RESET、PING/PONG。目标 IP 和端口只在 OPEN 中发送；后续 DATA 用 stream_id 找到目标连接，不重复携带 IP。字节内容不变，但仍需帧边界区分数据与心跳；不是裸 IP 包隧道，也不支持 UDP。

VPS 可接收并排队多个打印任务，依次打开目标流发送；一个流不等于一个打印指令。打印、扫描、运维代理竞争同一个活动流，打印优先、扫描逐目标排队。代理入口只监听 VPS 本机或受 SSH/VPN 保护，不开放无认证公网代理。

现有 HTTPS 轮询是已实现的旧设备路径，保留兼容；新网关不实现该路径，不把它用作自动恢复投递，避免双路径重复打印。网络打印机是首版目标；UART/USB 打印机需要其他适配器，不属于本 TCP 网关固件。

### 3.3 Web 发起发现，VPS 完成识别

设备认证时报告 LAN IP/子网掩码/网关，VPS 推算候选 CIDR，用户确认授权范围后从 Web 发起扫描。VPS 枚举地址和端口，复用 OPEN/DATA；8266 只连指定目标并转发，不实现 PROBE，不枚举、不识别协议。

| 目标 | VPS 执行的探测 | 结果含义 |
| --- | --- | --- |
| 9100/TCP | OPEN 成功后关闭，不发送任何打印字节 | 仅证明开放，不能确认打印机 |
| 631/TCP | 经 DATA 发送 IPP Get-Printer-Attributes 并解析响应 | 打印机名称、型号、能力证据 |
| 515/TCP | 已知队列的只读查询，不提交作业 | LPD 服务证据 |
| 80/443 TCP | VPS 请求并解析只读管理页面；HTTPS 的 TLS 由 VPS 客户端完成 | 厂商/型号线索，可能是其他设备 |
| 161/UDP | 首版不支持 UDP | 不依赖 SNMP |

页面显示 confirmed/probable/unknown 和证据，用户确认后在 VPS 保存 printer_id→设备 ID、当前 IP/端口绑定。业务请求使用 printer_id；DHCP 变更后重新发现。扫描串行、受超时/授权范围约束，可在目标之间取消，不打断正在发送的打印流。

## 4. 五个逻辑模块

### 4.1 打印指令接入服务

职责：

- 接受外部系统提交的结构化打印指令。
- 校验打印模板、打印机目标、业务单号和幂等键。
- 创建 `PrintJob`，初始状态为 `accepted`。
- 提供查询单个任务和提交结果的接口。

不负责排版，也不直接连接 ESP8266。接入成功只代表任务已持久化，不代表已经打印。

推荐入口：`POST /api/v1/print-commands`。

兼容入口：TCP `0.0.0.0:9100`，编码 GBK，消息为换行分隔的文本。兼容入口不依赖 HTTP 返回值；接收完成后先持久化任务，再由队列异步渲染和打印。

### 4.2 打印文件渲染服务

职责：

- 根据模板、订单数据和打印机能力生成打印产物。
- 处理纸张宽度（例如 58/76/80 mm）、字体、中文编码、换行、分页和二维码/条码。
- 记录渲染版本、模板版本和产物校验值。
- 渲染失败时保存可读错误原因，并允许后台重试。

首版建议生成打印机可以直接执行的 `ESC/POS` 字节流；ESP8266 只需流式转发，不需要理解 PDF 或图片。若某型号打印机需要 Linux 驱动或 Java AWT/CUPS，则把它作为服务端的另一个渲染/打印适配器，不强行让 ESP8266 解析桌面打印协议。

同一任务可以同时生成两种产物：

- `device_artifact`：给 ESP8266 打印的设备格式，首选 ESC/POS。
- `preview_artifact`：给后台预览的 PDF/PNG，可选，不参与设备投递。

### 4.3 VPS 隧道网关与业务调度

- 接收 TLS 连接、认证设备、维护在线 session 和心跳，拒绝旧会话覆盖新状态。
- 提供内部 open(device_id, target_ip, target_port) 字节流接口，校验授权、执行单流排队和流控。
- 打印 Worker 在 VPS 领取任务、读取产物并通过流输出；保存投递记录和不确定结果，不要求 8266 上报任务事件。
- VPS 扫描器借助相同流接口执行协议探测，解析响应与保存绑定。
- 已有 HTTPS poll/产物/events 接口保留给旧设备，新网关固件不调用。数据库租约和旧设备完成事件不能当作新隧道打印结果。

### 4.4 ESP8266 通用 TCP 网关

- 主动连接 VPS，校验证书、认证、心跳与退避重连。
- 解析有界帧，校验最小本地目标策略，最多维护一个目标 TCP socket。
- 按 OPEN 的 IPv4/端口连接，转发 DATA，处理信用窗口、半关闭和 RESET。
- 上报连接/传输错误与 LAN 信息；不扫描、不解析业务、不存储或去重打印任务。

设备仅使用固定大小流缓冲；打印文件的 SHA-256、打印确认和业务重试由 VPS/目标协议负责。TCP 写入成功不等于打印出纸。

### 4.5 后台 Web 查询页面

首版以查询和运维为主，页面至少包括：

- 任务列表：按时间、业务单号、设备、状态筛选。
- 任务详情：原始指令、渲染信息、投递尝试、错误信息和时间线。
- 设备列表：在线状态、最后连接/心跳时间、固件版本、打印机状态。
- 任务详情中的预览图或 PDF（如果生成了 `preview_artifact`）。
- 重试渲染、重试投递、取消未执行任务。

后台操作必须经过权限控制，并记录操作人和操作时间。页面不直接访问设备，也不绕过任务状态机写数据库。

## 5. 核心领域模型

### 5.1 实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `PrintJob` 打印任务 | 一次业务打印请求 | `id`、`idempotency_key`、`source`、`template_id`、`payload`、`target_device_id`、`status`、时间戳 |
| `PrintTemplate` 打印模板 | 定义数据到打印内容的映射 | `id`、`version`、`format`、`paper_width`、启用状态 |
| `RenderedArtifact` 渲染产物 | 某任务的设备文件或预览文件 | `job_id`、`kind`、`media_type`、`size`、`sha256`、存储位置 |
| `Device` 设备 | 一个 ESP8266 控制板 | `id`、设备凭据、固件版本、能力、最后在线时间 |
| `Printer` 打印机 | 连接在设备上的打印机 | 型号、连接类型、纸宽、协议、状态 |
| `DeliveryAttempt` 投递尝试 | 一次设备领取和执行记录 | `job_id`、`device_id`、租约、开始/结束时间、结果、错误 |
| `AuditEvent` 审计事件 | 重要状态和后台操作记录 | 操作者、动作、对象、时间、结果 |

### 5.2 任务状态

```text
accepted -> rendering -> queued -> leased -> printing -> succeeded
               |           |          |          |
               v           v          v          v
          render_failed  cancelled  expired  failed
```

新隧道路径需补充 sent（已发送）与 unknown（结果未知）状态及迁移；当前数据库/旧设备事件代码尚未实现这些新语义。

建议将渲染状态和投递状态分别存储，业务展示再汇总为任务状态。这样渲染成功但设备暂时离线时，任务仍然明确处于 `queued`，不会被误判为失败。

状态约束：

- `accepted`：指令已保存，尚未开始渲染。
- `rendering`：有一个渲染 Worker 持有渲染租约。
- `queued`：已生成设备产物，等待VPS 调度器等待目标隧道可用。
- `leased`：VPS Worker 持有投递租约（旧路径由设备领取）。
- `printing`：VPS 正经目标流发送打印字节。
- `succeeded`：VPS 通过目标协议确认完成；仅转发成功不能置为成功。
- `render_failed`：渲染失败，可修复后重试。
- `failed`：设备或打印机执行失败，按策略重试或人工处理。
- `expired`：Worker 租约超时；只有确认未投递的任务才能自动回队，已发送字节的结果先置未知待确认。
- `cancelled`：尚未实际打印的任务被取消。

## 6. 通用隧道协议与流程

> 详细协议同步于 PROTOCOL.md；本节为 v1 草案，尚未实现。

### 6.1 职责与连接边界

ESP8266 仅负责 TLS/设备认证、按目标 IPv4/端口建立 LAN TCP、双向原样转发、连接状态、流控、心跳和重连。VPS 负责渲染、任务存储、授权、扫描调度、协议识别及打印结果判断。不部署 MQ，不实现 `TASK_*`、`EVENT` 或 `PROBE` 帧。

```text
VPS 业务 / 扫描器          VPS 隧道网关              ESP8266            LAN 目标
        |                       |                      |                  |
        |                       |<-- 主动 TCP :9443 ---|                  |
        |                       |<==== TLS 握手 ======>|                  |
        |                       |<------ AUTH ---------|                  |
        |                       |------- AUTH_OK ----->|                  |
        | 请求目标 IP:端口       |                      |                  |
        |---------------------->|------- OPEN -------->|-- TCP connect -->|
        |                       |<------ OPEN_OK ------|                  |
        | 原始业务字节           |------- DATA -------->|-- 原始字节 ----->|
        |<----------------------|<------ DATA ---------|<-- 原始响应 ------|
        |                       |<------ PING ---------|                  |
        |                       |------- PONG -------->|                  |
        | 发送端结束             |------- FIN --------->|-- shutdown 写端 ->|
        |                       |<------ FIN ----------|<-- EOF -----------|
        |                       |<------ CLOSED -------| 已排空并关闭       |
```

TLS 加密仅覆盖 VPS 与 ESP8266，TLS 在这两端终止。LAN 连接由 ESP8266 建立；其字节是否另有加密取决于目标协议（RAW 打印通常明文，HTTPS/SSH 可由 VPS 的上层客户端端到端加密）。VPS 不直接连接 LAN 地址。

首版每设备最多一个活动流，连接建立中和关闭中也占用这个名额。控制帧可以与这个流交错；不是多个业务 TCP 连接的并发多路复用。一个流对应一对 TCP 端点，大文件和多个业务请求不必对应多个流。

### 6.2 固定帧头

TLS 内使用二进制帧。所有整数为无符号、网络字节序；固定头 16 字节，后接 `payload_length` 字节内容。

| 偏移 | 长度 | 字段 | 规则 |
| --- | --- | --- | --- |
| 0 | 2 | magic | ASCII `IT`，十六进制 `49 54` |
| 2 | 1 | version | `1` |
| 3 | 1 | type | 下表消息类型 |
| 4 | 4 | stream_id | 控制帧为 0；目标流为非零 |
| 8 | 4 | payload_length | DATA 最大 1024 字节；其他帧最大 512 字节 |
| 12 | 4 | reserved | 必须为 0 |

接收方增量读头、校验类型和长度，再读内容，不能按一次 `read/write` 判断消息边界。错误 magic、版本、保留位、未知类型、非法长度或无效状态直接关闭会话并释放目标；先验长度后分配内存，不尝试在任意业务数据中重新找帧头。TLS 已提供传输完整性保护，不另加自制加密或帧 CRC。

### 6.3 帧类型与内容

除 `DATA` 与空内容帧外，payload 为 UTF-8 JSON 对象，字段名固定；拒绝重复 JSON 键，所有必填字段都要校验。ID 是短 ASCII 字符串；错误信息不能携带密钥。

| type | 名称 | 方向 | stream_id / payload |
| --- | --- | --- | --- |
| 0x01 | AUTH | 设备→VPS | 0 / device_id、credential、firmware、lan_ip、netmask、gateway |
| 0x02 | AUTH_OK | VPS→设备 | 0 / session_id、heartbeat_sec=30、timeout_sec=90、initial_window=4096 |
| 0x03 | AUTH_ERROR | VPS→设备 | 0 / code |
| 0x10 | OPEN | VPS→设备 | 非零 / target_ip、target_port、connect_timeout_ms、idle_timeout_sec、initial_window=4096 |
| 0x11 | OPEN_OK | 设备→VPS | 同 OPEN / initial_window=4096 |
| 0x12 | OPEN_ERROR | 设备→VPS | 同 OPEN / code |
| 0x20 | DATA | 双向 | 非零 / 1--1024 字节原始数据 |
| 0x21 | WINDOW_UPDATE | 双向 | 非零 / credit，正整数，单次最多 4096 |
| 0x22 | FIN | 双向 | 非零 / 空，表示此方向没有更多 DATA |
| 0x23 | CLOSED | 设备→VPS | 非零 / 空，目标资源已释放，流可回收 |
| 0x24 | RESET | 双向 | 非零 / code，立即异常结束 |
| 0x30 | PING | 设备→VPS | 0 / nonce，递增 uint32 |
| 0x31 | PONG | VPS→设备 | 0 / 原样返回 nonce |

AUTH 中 device_id 最长 64 字符，credential 最长 128 字符，firmware 最长 64 字符；JSON 整体仍不得超过 512 字节。凭据仅在校验证书后的 TLS 内发送；服务端比对每设备密钥摘要并限制认证尝试。初版 TLS 库建议 ESP8266 Arduino Core 的 BearSSL `WiFiClientSecure`，VPS 用服务端 TLS 实现；不调用跳过证书校验的 `setInsecure()`。

`target_ip` 只接受 IPv4 数字地址，`target_port` 为 1--65535；不做 DNS 解析。VPS 校验设备的授权 CIDR/端口，设备保留最小本地网段限制，拒绝广播、组播、回环、未指定地址和禁止的目标。设备报告的 LAN 信息只是网段候选，不自动授予扫描权限。

`stream_id` 在一个 TLS 会话内从 1 单调增加、不复用；耗尽则重新建会话。连接忙时新 OPEN 返回 `OPEN_ERROR(BUSY)`，保留原流。其他 OPEN_ERROR 包括 `DENIED`、`REFUSED`、`UNREACHABLE`、`CONNECT_TIMEOUT`。失败仅结束该 OPEN，不关闭正常隧道。已 CLOSED 的旧 stream_id 不得用于新 DATA；RESET 收尾期间允许读取并丢弃已经在途的旧流帧，禁止向目标转发，直到 CLOSED。

### 6.4 状态与关闭

```text
未连接 → TCP/TLS → 等待 AUTH_OK → 空闲
                                  |
                                OPEN
                                  v
                                建连中 --OPEN_ERROR--> 空闲
                                  |
                               OPEN_OK
                                  v
                                 转发
                           /               \
                      FIN /                 \ RESET/错误
                         v                   v
                       半关闭              异常回收 → 空闲
                         |
                 双向 FIN + 缓冲排空
                         v
                     CLOSED → 空闲

任意状态：隧道失效 → 关闭 LAN socket → 退避重连 → 新认证
```

OPEN_ERROR 的连接尝试立即回到空闲，不需要 CLOSED。OPEN 成功前不能发 DATA。FIN 必须排在该方向全部 DATA 后，接收方先排空待写缓冲，再对目标 socket 执行写半关闭；反方向继续接收直到 EOF。FIN 后不得再发送该方向 DATA，WINDOW_UPDATE 与控制帧仍允许。设备在双向 FIN 且缓冲排空、目标关闭后发送 CLOSED，VPS 收到后才开始下一流；设备必须先把该流全部帧排在 CLOSED 前，防止新旧数据交错。若板端库无法实现半关闭，首版实现需先解决该能力或明确协议兼容范围，不能静默把 FIN 当全关闭。

RESET 表示丢弃未发完数据并立即关闭目标，设备清理后发送 CLOSED；正常 TCP 缓冲排空不等于打印成功。关闭收尾默认上限 10 秒，超时发送 RESET(CLOSE_TIMEOUT)。其他 RESET 错误码包括 `TARGET_IO`、`FLOW_CONTROL`、`IDLE_TIMEOUT`。RESET 后不再发送旧流 DATA；VPS 需收到设备 CLOSED 或关闭重建隧道后才能 OPEN 下一流（异常 CLOSED 也仅表示资源已释放）。设备发送 RESET 时紧随 CLOSED；VPS 发送 RESET 时，设备仍需回 CLOSED；若 10 秒未收到 CLOSED 则重建隧道。

### 6.5 心跳、流控与串行性

认证等待上限 10 秒；每次 LAN 建连默认 1500 ms，可由 VPS 指定 200--5000 ms；必须采用非阻塞或短时间分步调用，建连中同样处理心跳。目标流默认 120 秒无业务数据则 RESET，心跳不续目标流的空闲时间；OPEN 的 idle_timeout_sec 默认 120，允许 5--3600 秒；VPS 可按业务显式配置。

设备每 30 秒发送一个新 nonce 的 PING，VPS 尽快返回 PONG；设备 90 秒没有收到匹配的 PONG 则重连，即使仍收到 DATA 也不覆盖此检测。VPS 90 秒无设备 PING 则关闭并标离线。协议状态、心跳和 I/O 在同一主循环协作处理，定时让出执行时间给 Wi-Fi 与看门狗；打印数据传输期间仍处理 PING/PONG。

每个方向起始信用额度为 4096 字节（OPEN 宣告 VPS 的接收额度，即设备→VPS；OPEN_OK 宣告设备的接收额度，即 VPS→设备）；发送 DATA 消耗该方向额度。接收方只有在字节已被下一跳 socket 的 write 接受并腾出自身缓冲后，才发送 WINDOW_UPDATE 返还对应额度。额度不得超过初始窗口；超额 DATA/信用视为流控错误。每方向最多 4096 字节未消费数据，另留独立小型控制队列，避免业务缓冲满导致无法读取心跳。初始值是实机待验证的上限配置，TLS 自身缓冲另算。

每帧写出必须串行且完整，允许部分 write 后继续；心跳可在 DATA 帧之间优先调度，不能插入半帧或越过已经入队的 TCP 字节。两个方向是全双工；首版“单流”限制不妨碍心跳。TCP 没有固定包长，1024 字节是协议 DATA 上限，不是 MSS/MTU；长文件连续拆为多帧，不在设备缓存整份文件，不计算业务 SHA-256。

### 6.6 断线与重试

同一 TCP 连接内的丢包、排序、重传由协议栈负责，应用不对 DATA 做重复重发或逐帧确认。WINDOW_UPDATE 仅为缓冲流控，不是持久化 ACK，更不是打印确认。TLS 断开后，所有流与未写完的字节都失效，不做透明续传或重放。

设备按 1、2、4、8、16、30 秒上限退避并加随机抖动重连，稳定在线 60 秒后重置退避；新 TLS 会话重新 AUTH。VPS 对同设备的新认证连接接管在线记录并关闭旧连接，拒绝旧会话回调更新新状态。认证失败继续限速退避，不密集重试。

VPS 保存任务、产物与投递记录，应用根据目标协议判断是否可重试。OPEN 失败且未发送业务字节可以重新安排；发送过打印字节后断线或未收到打印机明确成功反馈，结果标记“未知/待确认”，不自动重打以免重复出纸。TCP write 成功、WINDOW_UPDATE、CLOSED 都不能证明真实出纸。若业务协议要求 checksum/作业 ID，由 VPS 与打印机协议处理，ESP8266 不理解它们。

### 6.7 发现内网 IP：复用 OPEN/DATA

```text
Web                    VPS 扫描器                ESP8266          LAN 候选
 | 点击发现                |                       |                 |
 |------------------------>| 枚举授权 CIDR/端口      |                 |
 |                         |-- OPEN(IP,9100) ------>|-- TCP connect ->|
 |                         |<- OPEN_OK / ERROR ----|                 |
 |                         |-- FIN（不发打印数据） ->|-- 关闭写端 ---->|
 |                         |<- FIN/CLOSED ----------|                 |
 |                         |-- OPEN(IP,631) ------->|-- TCP connect ->|
 |                         |-- DATA(IPP只读请求) -->|-- 原字节 ------>|
 |                         |<- DATA(IPP响应) -------|<- 原字节 -------|
 |                         | VPS 解析名称/型号       |                 |
 |<-- 候选与证据，确认绑定 --|                       |                 |
```

扫描、打印、普通代理共用唯一流，由 VPS 排队调度；打印优先，扫描仅在流关闭后让出，不能插入正在打印的字节流。扫描一次一个目标；连接成功后如目标不主动 EOF，可在短收尾超时后 RESET，等待 CLOSED 后继续。VPS 可在下一个目标开始前暂停/取消扫描。

9100/TCP 仅连通性检查，绝不发送测试打印内容；开放端口只能算候选。631/TCP 使用 VPS 构造并解析的 IPP Get-Printer-Attributes；515/TCP 只在已知队列和只读操作范围内探测；80/443 页面由 VPS 发请求并识别，443 的 TLS 由 VPS 上层客户端经透明流与目标握手，校验证书。SNMP/广播 mDNS 等 UDP 不在本协议范围内。无法确认身份的设备保持 unknown，由用户确认绑定；IP 变化重新触发发现，不硬编码到固件。

### 6.8 实现顺序与验收

1. VPS 网关与 Linux 协议客户端：AUTH、OPEN、双向 DATA、信用窗口、关闭及心跳；用 echo 服务验证透明传输。
2. 故障验证：逐字节/合帧读取、部分写、越界帧、窗口耗尽、慢目标、半关闭、目标拒绝、TLS 断开、旧会话替换、单流 BUSY；校验接收字节与源数据一致。
3. ESP8266 固件与 VPS 联调：证书校验、watchdog、堆内存、持续转发和重连；特别验证慢目标时心跳不被业务缓冲饿死。
4. VPS 打印与发现适配：任务路由到目标、只读探测和结果未知处理。无目标协议确认前不承诺“恰好打印一次”。

以上是可实现的协议草案，不代表网关或固件已经完成；当前仓库设备端仍只有说明文档。

## 8. 安全与运维

- 外部 API 和设备 API 全部使用 HTTPS。
- 每台 ESP8266 使用独立设备 ID 和密钥；服务端不能用一个共享密钥代表所有设备。
- 设备接口只允许访问自己的任务和产物，后台接口使用独立账号/角色；反向代理入口必须经过 SSH/VPN 和目标策略控制。
- 打印数据按 JSON Schema 校验，限制字段长度、明细行数和产物大小，避免异常请求拖垮渲染 Worker。
- 记录结构化日志：任务 ID、设备 ID、租约 ID、状态变化和错误码，不把完整敏感打印内容写入普通日志。
- 监控待渲染数量、队列等待时间、渲染失败率、设备在线率、任务重试次数和打印成功率。
- 数据库定期备份；打印产物设置保留周期，避免磁盘无限增长。

## 9. 分阶段实施建议

### 阶段一：最小闭环

- 一个模板、一个设备、一个打印机型号。

- 必要时拆分渲染 Worker 与任务存储层。

## 10. 需要在实现前确认的问题

1. 首台打印机是否支持网络 TCP？首版通用网关只连 TCP 目标；UART/USB 需要另行适配。
2. 首台打印机的准确型号、纸宽和控制协议是什么？芯烨 58/80/76 系列与 `Jolimark FP-570K` 不能默认使用同一渲染器。
3. 打印内容是否只包含订单小票，还是还需要图片、二维码、条码、PDF 等格式？
4. 外部提交方是否已有固定的 TCP/GBK 协议，是否需要首版兼容端口 `7576` 或 `9600`？
5. 一个任务是否允许指定设备，还是由服务端按设备组/打印机类型自动路由？
6. 目标打印协议是否提供可验证的作业完成反馈？没有反馈时，VPS 只能区分已发送和结果未知。
7. 是否需要用户登录、多个角色和远程重打权限？

在这些问题确认前，本文中的接口路径和字段名属于方案草案，不作为最终兼容承诺。

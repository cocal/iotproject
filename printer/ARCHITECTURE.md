# 远程打印机项目总体方案

> 状态：设计稿 v0.4（设备反向 TCP 代理方案）
> 范围：只定义总体架构、领域模型、接口边界和运行流程，不包含实现代码。

## 1. 背景与目标

`iotproject` 是多个物联网项目的总仓库，本文件只描述其中的 `printer` 子项目。

目标是让外部系统提交打印指令，由远程服务端生成打印内容；ESP8266 主动连接远程服务端，既接收打印任务，也按经授权的目标地址和端口连接局域网服务并转发 TCP 流量，同时提供一个后台 Web 页面查询任务、设备和打印结果。

首版需要解决：

1. 打印指令可以被可靠接收并保存。
2. 打印内容在远程服务端统一渲染，设备端不承担复杂排版。
3. ESP8266 断线重连或重启时不会静默丢单。
4. 后台能够区分“未渲染、待打印、打印中、成功、失败”等状态。
5. 旧 Java 程序中的订单字段和热敏/针式打印布局可以逐步迁移。
6. 远程用户可经 VPS 上受认证的入口访问设备所在内网中明确授权的 TCP 服务。

## 2. 历史资料结论

历史打印机代码和二进制资料提供了以下约束：

- `Netkk.java` 在本地监听 TCP `7576`，使用 GBK 按行读取文本，收完连接后直接触发打印。
- JAR 中的 `NetworkServer_2` 默认使用 TCP `9600`，同样使用 GBK 按行读取，并以包含“地址”的行作为一份单据的触发标记。现网端口已确认为 **9100**，新服务端兼容入口使用 9100；9600 只作为旧 JAR 的历史默认值记录。
- 旧数据按订单字段和商品明细组织，字段包括序号、时间、客户、清单号、商品名、数量、单位、单价、金额、合计和备注。
- `Tt.java`/`PcpPrinter_2` 将排版写死在 Java AWT 打印代码中，并选择固定打印机名称，例如 `Jolimark FP-570K`。
- 目录中还有芯烨 58/80/76 系列 Linux 驱动，说明历史环境可能包含本地 Linux 打印机驱动和非纯 ESC/POS 打印机。

这些资料说明了业务字段和打印样式来源。新服务端在 9100 上保留独立的旧协议适配器：每个 TCP 连接使用 GBK 按行读取，连接关闭或检测到包含“地址”的行时形成一份原始单据，并将原始报文和解析结果写入 `PrintJob`。内部 API、数据库和设备协议仍使用结构化 JSON、UTF-8 和任务状态记录，避免让历史协议扩散到新模块。

## 3. 总体架构

```text
外部业务系统
      |
      | HTTPS: 提交打印指令
      v
远程服务端
  ├─ 打印接入 API
  ├─ 任务编排与状态机
  ├─ 渲染 Worker
  ├─ ESP8266 连接网关
  ├─ 后台查询 API
  └─ 数据库 + 打印文件存储
      ^                         |
      | 专用 TLS TCP 长连接       | 推送任务与打印数据
      | HTTPS 轮询作为恢复通道   v
 ESP8266 控制板  --串口/硬件接口-->  本地打印机
      |
      | ESP8266 主动发起目标连接，并在隧道上双向转发
      v
 局域网授权 TCP 服务
      ^
      |
 运维用户（经 SSH/VPN 访问 VPS 上的 SOCKS5/转发入口）
```

### 3.1 部署建议

逻辑上分为五个模块，首版部署为两个运行单元：

- `server-api`：打印接入、任务状态、设备连接网关、后台 API，以及 Web 静态文件或 Web 反向代理。
- `render-worker`：从数据库领取待渲染任务，生成可供设备打印的文件或字节流。

数据库使用 PostgreSQL 保存打印任务和投递状态；首版不额外部署 Redis 或消息代理。渲染产物可以存放在服务器文件系统，接口保留对象存储替换点；任务量变大后再评估数据库队列和渲染 Worker 的扩展方式。

### 3.2 ESP8266 任务通信方案比较与决策

这里需要区分两种“透传”：ESP8266 收到打印字节后通过 UART 转发给本地打印机，是打印代理的一种流；运维用户经 VPS 请求访问设备所在局域网的任意授权 TCP 服务，则是反向 TCP 代理流。两种流都复用设备主动建立的 TLS 控制连接，但代理流和打印任务使用不同的消息类型与状态处理。

| 方案 | 通信路径与延迟 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| HTTPS 轮询 | ESP8266 主动向服务端请求；按 5 秒间隔时，新任务通常在 0--5 秒内被发现，平均约 2.5 秒 | 实现简单；可穿过普通 NAT、家庭路由器和 CGNAT；断线后下一次请求自然恢复；沿用现有设备鉴权、租约、任务事件和重试逻辑 | 空闲设备也会周期性请求；100 台设备按 5 秒间隔约产生 20 次轮询/秒；不适合要求亚秒级通知的场景 |
| ESP8266 主动建立的反向 TCP 代理 | ESP8266 主动连 VPS 的 TLS TCP 端口（例如 `9443`）；运维用户请求访问某个目标时，VPS 经控制连接发送目标地址/端口，ESP8266 再主动连接局域网目标并双向转发数据 | 无需局域网公网地址、路由器端口映射或 MQ；可访问授权范围内的不同内网 TCP 服务；同一隧道可以承载打印任务和代理流 |
| 公网端口映射 | 路由器将公网端口映射到内网主机/打印机 | 配置少、无需设备固件实现隧道协议 | 依赖公网可入站地址，CGNAT 下通常不可用；扩大内网设备暴露面；设备网络需要逐一配置端口映射 |

**首版决策：将 ESP8266 实现为受控的通用内网 TCP 代理，不部署 MQ。** ESP8266 主动建立到 VPS 的 TLS TCP 控制连接。打印任务由服务端沿该连接下发；运维用户经 SSH/VPN 访问 VPS 上的 SOCKS5 或端口转发入口，VPS 将用户请求的目标地址/端口通过隧道发给 ESP8266，ESP8266 在局域网内主动建立目标 TCP 连接并双向转发。

当前仓库已经实现 HTTPS `poll`，TCP 代理网关和 SOCKS5 入口尚未实现；长连接不可用时，打印任务仍可通过现有 HTTPS 接口恢复。通用代理是独立于打印任务队列的流量转发能力，连接断开时代理流会关闭，不应把任意 TCP 流错误地记为打印任务。

设备控制隧道使用独立端口（建议从 `9443/TCP` 开始），因为 VPS 的 `443/TCP` 已由 Nginx 提供 HTTPS 网站服务。VPS 上的 SOCKS5/代理入口只绑定 `127.0.0.1`，运维用户通过 SSH 或 VPN 访问，不直接向公网开放。启用隧道时需开放 VPS `nftables` 与云安全组的 `9443/TCP`；ESP8266 只需主动出站连接。若设备网络限制该端口，可用现有 HTTPS 轮询恢复打印任务，但不能经轮询承载通用 TCP 代理流。

隧道使用带长度的应用层帧。设备上线后发送设备 ID、固件版本和独立凭据，VPS 完成鉴权并登记活动控制连接；双方用心跳检测断线。代理请求使用 `OPEN(stream_id, target_ip, target_port)`，设备按本地授权策略校验目标并连接后返回 `OPEN_OK` 或 `OPEN_ERROR`；数据用 `DATA(stream_id, bytes)` 双向转发，并使用 `CLOSE`、`RESET`、`WINDOW_UPDATE` 控制关闭、错误和流量背压。控制消息与数据流通过 `stream_id` 多路复用在设备发起的 TLS TCP 连接上。

ESP8266 固件负责 Wi-Fi/TLS、连接保活、断线指数退避重连、帧解析、代理目标连接、数据转发和打印机 UART；VPS 隧道网关负责 TLS 服务端、设备鉴权、活动连接登记、SOCKS5/转发入口、目标访问控制和流多路复用；Spring Boot 与 PostgreSQL 继续负责任务队列、打印租约、状态机和重试。VPS 入口应先通过 SSH/VPN 身份认证，再创建目标流；设备侧也校验目标 CIDR/端口，避免 VPS 控制面错误或凭据泄露后无约束访问局域网。

代理目标策略由服务端与设备配置共同约束：目标地址采用明确允许的内网 CIDR/主机列表，端口采用允许列表；首版建议只支持 IPv4 字面地址，避免设备端 DNS 解析带来的重绑定和地址检查歧义。拒绝 VPS 自身、环回、链路本地、云元数据地址和非允许网段；记录请求用户、设备、目标 IP/端口、开始/结束时间、流量和结果；设置空闲超时、单设备并发上限与带宽/连接数限制。规则可配置扩展为用户所需的内网范围，但 SOCKS5 入口不能成为无认证的公网开放代理。

由于 ESP8266 可用内存有限，第一版先实现一个设备同时承载一个代理流，代理数据帧上限从 512 字节开始，并用窗口/背压避免慢速内网目标导致内存队列增长；通过真实硬件测试后再评估多流和帧大小。每个代理连接需要占用一个本地 TCP socket 和转发缓冲区。打印任务保持自己的 `task_id`、租约、应用层 ACK 和至少一次投递语义；打印机已出纸但完成 ACK 丢失时仍可能需要人工判断。

通用 TCP 隧道不代表 VPS 直接“看见”或扫描整个局域网：每条流都由经过认证的运维请求显式指定目标，并由设备按策略决定是否建立连接。设备离线时，代理会话结束；打印任务按租约恢复。两种流量共用安全的 TLS 控制连接，但使用不同消息类型和状态处理。

## 4. 五个逻辑模块

### 4.1 打印指令接入服务

职责：

- 接受外部系统提交的结构化打印指令。
- 校验打印模板、打印机目标、业务单号和幂等键。
- 创建 `PrintJob`，初始状态为 `accepted`。
- 提供查询单个任务和提交结果的接口。

不负责排版，也不直接连接 ESP8266。接入成功只代表任务已持久化，不代表已经打印。

推荐入口：`POST /api/v1/print-commands`。

兼容入口：TCP `0.0.0.0:9100`，编码 GBK，消息为换行分隔的文本。兼容入口不依赖 HTTP 返回值；接收完成后先持久化任务，再由队列异步渲染和打印。

### 4.2 打印文件渲染服务

职责：

- 根据模板、订单数据和打印机能力生成打印产物。
- 处理纸张宽度（例如 58/76/80 mm）、字体、中文编码、换行、分页和二维码/条码。
- 记录渲染版本、模板版本和产物校验值。
- 渲染失败时保存可读错误原因，并允许后台重试。

首版建议生成打印机可以直接执行的 `ESC/POS` 字节流；ESP8266 只需流式转发，不需要理解 PDF 或图片。若某型号打印机需要 Linux 驱动或 Java AWT/CUPS，则把它作为服务端的另一个渲染/打印适配器，不强行让 ESP8266 解析桌面打印协议。

同一任务可以同时生成两种产物：

- `device_artifact`：给 ESP8266 打印的设备格式，首选 ESC/POS。
- `preview_artifact`：给后台预览的 PDF/PNG，可选，不参与设备投递。

### 4.3 ESP8266 连接网关

职责：

- 设备注册、鉴权、心跳和能力上报。
- 接受 ESP8266 主动建立的 TLS TCP 连接，完成设备鉴权和心跳维护。
- 设备上线时登记活动连接；断开或心跳超时时清除连接状态。
- 收到新任务后为目标设备原子领取任务并经活动连接发送。
- 接收已认证的 SOCKS5/转发请求，通过设备连接发送目标地址/端口并多路复用数据流。
- 在 VPS 入口和设备侧分别执行目标 CIDR/端口授权、并发/速率限制和审计。
- 为任务发放短期租约，避免设备掉线后任务永久卡住。
- 接收设备的 `received`、`started`、`completed`、`failed` 事件。
- 根据设备状态和租约结果安排重试。
- 保留 HTTPS 轮询 API，作为长连接不可用时的恢复通道。

现有 HTTPS 恢复接口：

```text
POST /api/v1/devices/{device_id}/poll
POST /api/v1/devices/{device_id}/tasks/{task_id}/events
GET  /api/v1/devices/{device_id}/tasks/{task_id}/artifact
```

现有 HTTPS 恢复接口使用 `X-Device-Key` 独立鉴权，租约默认 120 秒。未来 TCP 长连接使用每设备独立凭据鉴权；应用层消息帧至少包含设备 ID、消息类型、长度、任务 ID 和租约 ID，并通过应用层 ACK 确认领取和最终结果。TCP ACK 不能当作打印结果确认。

### 4.4 ESP8266 本地打印代理

职责：

- 以设备凭据主动建立 TLS TCP 控制连接；网络失败时指数退避并持续重连。
- 解析有长度边界的多路复用帧；收到 `OPEN` 时校验目标策略，并主动连接目标内网 TCP 服务。
- 在 VPS 隧道和目标 socket 之间双向转发 `DATA` 帧，支持背压、关闭和超时。
- 对打印任务另外校验任务 ID、数据长度和 SHA-256，并按业务事件确认。
- 将打印任务发往 UART、USB 转接或配置好的打印机网络接口。
- 在本地记录最近完成的任务 ID，防止重启后重复打印。
- 上报打印机缺纸、离线、串口错误、超时等可观测状态。

ESP8266 不负责模板解析、PDF 解析或中文排版。若实际打印机只有 USB/CUPS 接口而没有 ESP8266 可用的串口/网络接口，需要增加本地 Linux 打印网关；这个硬件前提必须在实施前确认。

### 4.5 后台 Web 查询页面

首版以查询和运维为主，页面至少包括：

- 任务列表：按时间、业务单号、设备、状态筛选。
- 任务详情：原始指令、渲染信息、投递尝试、错误信息和时间线。
- 设备列表：在线状态、最后连接/心跳时间、固件版本、打印机状态。
- 任务详情中的预览图或 PDF（如果生成了 `preview_artifact`）。
- 重试渲染、重试投递、取消未执行任务。

后台操作必须经过权限控制，并记录操作人和操作时间。页面不直接访问设备，也不绕过任务状态机写数据库。

## 5. 核心领域模型

### 5.1 实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `PrintJob` 打印任务 | 一次业务打印请求 | `id`、`idempotency_key`、`source`、`template_id`、`payload`、`target_device_id`、`status`、时间戳 |
| `PrintTemplate` 打印模板 | 定义数据到打印内容的映射 | `id`、`version`、`format`、`paper_width`、启用状态 |
| `RenderedArtifact` 渲染产物 | 某任务的设备文件或预览文件 | `job_id`、`kind`、`media_type`、`size`、`sha256`、存储位置 |
| `Device` 设备 | 一个 ESP8266 控制板 | `id`、设备凭据、固件版本、能力、最后在线时间 |
| `Printer` 打印机 | 连接在设备上的打印机 | 型号、连接类型、纸宽、协议、状态 |
| `DeliveryAttempt` 投递尝试 | 一次设备领取和执行记录 | `job_id`、`device_id`、租约、开始/结束时间、结果、错误 |
| `AuditEvent` 审计事件 | 重要状态和后台操作记录 | 操作者、动作、对象、时间、结果 |

### 5.2 任务状态

```text
accepted -> rendering -> queued -> leased -> printing -> succeeded
               |           |          |          |
               v           v          v          v
          render_failed  cancelled  expired  failed
```

建议将渲染状态和投递状态分别存储，业务展示再汇总为任务状态。这样渲染成功但设备暂时离线时，任务仍然明确处于 `queued`，不会被误判为失败。

状态约束：

- `accepted`：指令已保存，尚未开始渲染。
- `rendering`：有一个渲染 Worker 持有渲染租约。
- `queued`：已生成设备产物，等待目标设备可用连接领取。
- `leased`：设备已领取，服务端等待设备确认开始或完成。
- `printing`：设备已开始向打印机输出。
- `succeeded`：设备确认打印机完成。
- `render_failed`：渲染失败，可修复后重试。
- `failed`：设备或打印机执行失败，按策略重试或人工处理。
- `expired`：设备租约超时，任务回到 `queued` 或进入失败重试。
- `cancelled`：尚未实际打印的任务被取消。

## 6. TCP 代理与打印任务流程

### 6.1 内网 TCP 代理流程

1. ESP8266 主动连接 VPS `9443/TCP`，使用 TLS 和设备独立凭据鉴权，随后发送心跳。
2. 运维用户先经 SSH/VPN 进入 VPS，再连接仅监听 `127.0.0.1` 的 SOCKS5/转发入口。
3. VPS 认证用户并验证其设备、CIDR 和端口权限后，分配 `stream_id`，发送 `OPEN(stream_id, target_ip, target_port)`。
4. ESP8266 再校验设备侧目标策略，并用本地 Wi-Fi 建立到目标的 TCP socket；连接成功返回 `OPEN_OK`，失败返回错误码。
5. VPS 和 ESP8266 将两端字节分别包装成 `DATA(stream_id, bytes)` 帧；`WINDOW_UPDATE`/背压限制缓冲区，避免慢速目标耗尽 ESP8266 内存。
6. 一端关闭时发送 `CLOSE`；异常或超时则发送 `RESET` 并释放目标 socket 和流状态。

代理流是临时会话，不创建 `PrintJob`，也不由打印租约重试。控制隧道断开后，所有代理流关闭，由运维客户端按原协议自行重连。

### 6.2 一次打印任务流程

1. 外部系统提交指令，服务端以幂等键创建 `PrintJob`，完成渲染后将任务设为 `queued`。
2. 连接网关在活动设备连接上发送任务元数据和分块打印数据；ESP8266 校验任务 ID、数据长度和 SHA-256 后回复 `received`。
3. ESP8266 向打印机输出前上报 `started`，完成后上报 `completed` 或 `failed`。
4. 服务端记录投递尝试，任务进入终态或按租约/重试策略重新排队。打印任务连接不通过 SOCKS5 目标请求路由，使用预配置的打印机接口。

### 6.3 断网、重启和重复任务

- TCP 应用层消息、事件上报和创建打印任务都要支持幂等标识；轮询恢复接口也应使用同一任务 ID 和租约规则。
- 租约必须有过期时间，例如 2 分钟；过期任务不能永久占用队列。
- 服务端定期回收过期租约；任务在 `max_attempts` 内回到 `queued`，超过次数进入 `failed` 并保留错误原因。
- 设备在本地保存最近若干个已完成任务 ID。服务端重复返回同一个任务时，设备只确认已完成，不再次打印。
- 服务端采用“至少一次投递”语义，不能承诺网络故障下的严格一次打印。通过幂等任务 ID、设备去重和可见的投递记录降低重复打印风险。
- 对无法确认打印机是否已经出纸的超时，只能标记为 `uncertain`/`failed` 并交给后台人工确认，不能盲目自动重打。

### 6.4 设备响应大小

ESP8266 内存有限，不能假设一次响应可以装下完整 PDF 或大图片。设备产物接口应支持分块读取（建议每块 1--4 KB），服务端返回总长度和 SHA-256；设备可以使用 LittleFS 暂存，也可以边下载边发送，具体取决于打印机协议和断点续传需求。

```json

```

### 7.2 HTTPS 轮询恢复响应

下面的轮询接口是当前代码已经实现的恢复通道；专用 TLS TCP 连接网关尚未实现。正常情况下，设备保持长连接接收服务端推送的任务。

```json
{
  "server_time": "2026-10-24T12:00:00Z",
  "poll_after_ms": 5000,
  "task": {
    "task_id": "job_01...",
    "lease_id": "lease_01...",
    "expires_at": "2026-10-24T12:02:00Z",
    "artifact_url": "/api/v1/devices/printer-room-1/tasks/job_01.../artifact",
    "size": 1832,
    "sha256": "...",
    "format": "escpos"
  }
}
```

无任务时 `task` 为 `null`。仅在长连接无法建立或断开时使用恢复轮询；服务端可以通过 `poll_after_ms` 调整间隔。

## 8. 安全与运维

- 外部 API 和设备 API 全部使用 HTTPS。
- 每台 ESP8266 使用独立设备 ID 和密钥；服务端不能用一个共享密钥代表所有设备。
- 设备接口只允许访问自己的任务和产物，后台接口使用独立账号/角色。
- 打印数据按 JSON Schema 校验，限制字段长度、明细行数和产物大小，避免异常请求拖垮渲染 Worker。
- 记录结构化日志：任务 ID、设备 ID、租约 ID、状态变化和错误码，不把完整敏感打印内容写入普通日志。
- 监控待渲染数量、队列等待时间、渲染失败率、设备在线率、任务重试次数和打印成功率。
- 数据库定期备份；打印产物设置保留周期，避免磁盘无限增长。

## 9. 分阶段实施建议

### 阶段一：最小闭环

- 一个模板、一个设备、一个打印机型号。
- 接入 API、PostgreSQL 任务表、ESC/POS 渲染、专用 TLS TCP 设备连接和完成/失败上报。
- 后台只提供任务和设备查询。
- 使用设备独立凭据；设备到服务端采用 TLS，HTTPS 轮询作为断线恢复通道。

### 阶段二：可运维化

- 模板版本和预览产物。
- 任务重试、取消、手动重打和审计记录。
- 设备能力上报、打印机状态和更完整的后台筛选。
- 旧 TCP/GBK 协议适配器，作为迁移期兼容层。

### 阶段三：多设备与多型号

- 多打印机配置和渲染适配器。
- 分组、优先级、按设备路由和并发控制。
- 对大文件增加断点续传和对象存储。
- 必要时拆分渲染 Worker 与任务存储层。

## 10. 需要在实现前确认的问题

1. ESP8266 与打印机的实际连接方式是 UART、USB 转接、网络，还是通过本地 Linux 主机？这决定设备代理能否直接发送 ESC/POS。
2. 首台打印机的准确型号、纸宽和控制协议是什么？芯烨 58/80/76 系列与 `Jolimark FP-570K` 不能默认使用同一渲染器。
3. 打印内容是否只包含订单小票，还是还需要图片、二维码、条码、PDF 等格式？
4. 外部提交方是否已有固定的 TCP/GBK 协议，是否需要首版兼容端口 `7576` 或 `9600`？
5. 一个任务是否允许指定设备，还是由服务端按设备组/打印机类型自动路由？
6. “打印完成”的定义是 ESP8266 发完字节，还是需要打印机提供真实的出纸/故障反馈？
7. 是否需要用户登录、多个角色和远程重打权限？

在这些问题确认前，本文中的接口路径和字段名属于方案草案，不作为最终兼容承诺。
